# «Круг»: обзор проекта и основания для задания Codex

Дата: 13 ноября 2026 года, Владивосток. Изученный коммит: `709cdf4`.

## Что уже есть

Проект сейчас представляет собой локальный Data Studio для MongoDB. Это техническая основа будущего сервиса, а предметная область обменов ещё не реализована.

| Область | Фактическое состояние |
| --- | --- |
| Интерфейс | Next.js 16.4.6, React 19.3.0, TypeScript, App Router. Главная страница открывает `DatabaseStudio`. |
| Сервер | Отдельный Express 5 в корневой папке `server/`, запуск через `tsx`. |
| Хранилище | Драйвер `mongodb` 6.22, база `vibe_farpost`, локальный порт 27018. При проверке была только `_collections` с 0 документов. |
| Запуск MongoDB | `scripts/mongodb.mjs`, файлы в `.local/mongodb/`. По коду запускается standalone, без `--replSet`. |
| API | `/api/db/health`, коллекции, определения полей и CRUD документов. Next.js проксирует `/api/db/*` на порт 4000. |
| Формы | Динамические поля: текст, длинный текст, число, логическое значение, дата, ссылка. Массивов, вложенных доменных объектов и отношений в этом редакторе нет. |
| Валидация | Zod, проверка имён, типов, обязательных полей, дат и URL, ограничение размера запроса. |
| Ограничения доступа | Loopback, проверка Host/Origin и служебного заголовка. Это ограничения локального инструмента, а не аутентификация пользователей. |
| Тесты | Девять интеграционных тестов MongoDB и один браузерный сценарий Data Studio с мобильным экраном. |
| Структура | Клиент в `src/`, сервер в `server/`, общие типы в `shared/`, скрипты и тесты вынесены отдельно. |
| Git | `main` отслеживает `origin/main`. В начале исследования рабочая папка была чистой. `.env`, `.local`, зависимости и сборки исключены из Git. |

Изучены маршруты, подключение базы, проверки входных данных, компоненты интерфейса, стили, запуск, конфигурация Next.js, документация и оба набора тестов. `npm run lint` и `npm run typecheck` прошли во время этого исследования. Интеграционные и браузерные тесты в этот раз не запускались: для подготовки задания менять данные не требовалось.

Изначально MongoDB была выключена. Для завершения обзора она временно запущена штатной командой: проверены только имена коллекций и количество документов. В базе `vibe_farpost` найдена одна системная коллекция `_collections`, в ней 0 документов. После проверки запущенный для исследования процесс остановлен; прикладные данные не создавались и не менялись. Будущий исполнитель всё равно должен перепроверить состояние: после этого снимка команда может добавить данные.

## Как читать критерии

Источник критериев — пять приложенных командой слайдов. Дополнительных правил мероприятия и ограничения длительности выступления в исходных данных нет.

| Критерий | Баллы | Что должно стать доказательством |
| --- | ---: | --- |
| Работоспособность MVP | 12 | Реальная цепочка: заявка → поиск → круг → ответы участников → согласие или отказ и новый вариант. |
| Технические решения | 8 | Типизированный домен, объяснимое сопоставление, корректные циклы 2–4, сохранение в MongoDB, обоснованная защита от конфликтов. |
| Как применяли ИИ | 10 | Реальные примеры помощи ИИ и проверок результата: алгоритм, граничные случаи, тесты, исправления. Встраивание LLM в сервис не является условием слайда. |
| Надёжность и безопасность | 5 | Серверная идентификация, права владельца, валидация, ошибки, защита от повторных действий и двойного резервирования. |
| Кто пользователь и в чём проблема | 8 | Житель с ненужной вещью и конкретной потребностью; проблема взаимного совпадения желаний показана на примере. |
| Качество решения и сценария | 12 | Понятные формы и ограничения, объяснения совпадений, наглядный круг, видимый следующий шаг. |
| Осмысленность продуктовых решений | 10 | Зафиксированы гипотеза, границы MVP, компромиссы и следующий эксперимент. |
| Значимость городской проблемы | 8 | Понятный сценарий местного повторного использования вещей. Масштаб проблемы требует проверки, а не выдуманных чисел. |
| Применимость в городских условиях | 8 | Территории встречи, готовность к поездке/самовывозу, совместимость времени, местное время Владивостока. |
| Как измерить результат | 4 | Воспроизводимое сравнение прямого и многостороннего подбора; согласия отделены от реально состоявшихся обменов. |
| Креативность и презентация | 15 суммарно | История «проблема → решение → результат», живой показ, содержательные ответы, визуализация, помогающая понять идею. На слайде нет отдельных весов четырёх подпунктов. |

Техническая реализация и продукт вместе дают 65 баллов. Сначала нужен законченный обменный сценарий, затем оформление и дополнительные возможности.

## Решения, заложенные в промпт

1. Сохранить существующую инфраструктуру; Data Studio перенести на `/studio` и отделить от бизнес-данных.
2. Ввести самостоятельные типизированные модели обменов. Динамические формы администратора не заменяют доменные схемы и правила переходов состояний.
3. Сделать текстовые заявки с небольшим набором структурированных уточнений. Категории, типы вещей и словарь синонимов помогут воспроизводимо сопоставлять русские описания без обязательного внешнего ИИ API.
4. Искать простые ориентированные циклы с разными владельцами. Направление стрелки означает передачу вещи: для исходного примера правильный порядок — монитор → владелец дрели → владелец велосипеда → владелец монитора.
5. Проверять общую возможность встречи всего круга. Попарная совместимость времени не доказывает наличие общего времени для трёх или четырёх людей.
6. Не резервировать вещи при простом показе результата. После согласия всех участников атомарно закреплять их за кругом, защищая от конкурирующих подтверждений.
7. Для транзакций предусмотреть локальный replica set из одного узла. Текущий standalone не поддерживает многодокументные транзакции. Один узел нужен для локального прототипа и не создаёт отказоустойчивую инфраструктуру.
8. Отделить «все заинтересованы» от «вещи переданы». В MVP проверяется первая стадия; нельзя записывать её в статистику завершённых обменов.
9. Для показа дать явный локальный деморежим со сменой вымышленных участников; каждый ответ всё равно проходит через серверную сессию текущего участника.
10. Отказ должен исключать отклонённую комбинацию в той же версии, а не закрывать человеку возможность любых других обменов.

Это предложенные продуктовые и технические решения для MVP, а не дополнительные условия организаторов. Команда может изменить их до начала реализации.

## Проверка демонстрационного графа

Набор заявок из основного промпта проверен отдельным перебором ориентированных циклов длиной 2–4. При одинаковых совместимых ограничениях и точном совпадении типов найдены ровно четыре цикла с точностью до поворота:

- `A → C → B → A` — основной трёхсторонний обмен;
- `A → E → D → A` — другой вариант после отказа B;
- `F → I → H → G → F` — обмен четырёх участников;
- `J → K → J` — прямой обмен.

У A нет прямого обмена. У L нет замкнутого пути. Это проверка согласованности синтетического сценария, а не проверка будущего производственного алгоритма или подтверждение спроса горожан.

В этом учебном графе потенциальный вариант есть у 2 из 12 владельцев при поиске только пар и у 11 из 12 при поиске 2–4 участников. Это объединение участников всех найденных вариантов, включая пересекающиеся круги: число не означает, что все эти обмены можно провести одновременно. В интерфейсе любые такие показатели должны рассчитываться по текущим данным и явно помечаться как демонстрационные.

## Неопределённости, которые нельзя выдавать за факты

- Насколько жителям нужен именно многосторонний обмен и готовы ли они координировать 3–4 человека.
- Достаточно ли локального предложения вещей для устойчивого появления кругов.
- Какие территории и условия встреч удобны будущим пользователям.
- Будут ли согласия превращаться в реальные обмены и сколько займёт координация.
- Ограничения публичного запуска, модерация, восстановление аккаунтов и работа с персональными данными выходят за текущий локальный демосценарий.

Следующий продуктовый эксперимент: небольшой добровольный пилот с реальными текстовыми заявками, проверка найденных кругов людьми, наблюдение за отказами и координацией встречи. Размер пилота и целевые конверсии команда должна выбрать до запуска; результаты пока отсутствуют.
