# Промпт для Codex: реализация MVP «Круг»

Ты работаешь в существующем репозитории `vibe-farpost`. Реализуй рабочий локальный веб-прототип «Круг» для Вайбатона, развивая имеющийся проект. Выполни реализацию, проверки и документацию, а не только план или макет.

Для визуального интерфейса используй `$krug-material-design`. Если навык ещё не появился в списке, прочитай `.agents/skills/krug-material-design/SKILL.md` напрямую и следуй указанным там справочникам. Короткие промпты активации находятся в `docs/ACTIVATE-DESIGN.md`.

Явный выбор UI-стека: Framework7 React с Material-темой для мобильных экранов, Material UI для десктопных. Обе оболочки используют общие доменные типы, API, сессии, состояние форм и дизайн-токены.

## 1. Продукт и результат

«Круг» — сервис многостороннего обмена вещами между жителями Владивостока. Человек указывает, что готов отдать, что хочет получить и какие условия ему подходят. Сервис ищет обмены между двумя, тремя или четырьмя разными участниками, объясняет найденный вариант и собирает подтверждения интереса.

Главная гипотеза: поиск многосторонних циклов обнаруживает варианты, которые не появляются при поиске прямой пары. Не представляй гипотезу как уже доказанный спрос.

Пример: у Анны монитор, нужен велосипед; у Бориса велосипед, нужна дрель; у Веры дрель, нужен монитор. Прямого обмена нет, но вещи можно передать по кругу так, чтобы каждый получил желаемое.

Готовый результат: с чистого запуска можно войти в локальное демо, создать текстовую заявку, найти реальный круг по данным MongoDB, увидеть передачи вещей, по очереди ответить от имени участников, получить согласованный круг либо после отказа найти другую комбинацию. Обновление страницы сохраняет результат.

## 4. Границы MVP

Обязательно реализуй:

1. Локальную идентификацию пользователя и явный деморежим со сменой вымышленных участников.
2. Создание, просмотр, редактирование и архивирование собственной текстовой заявки.
3. Каталог активных заявок, простые фильтры и раздел «Мои заявки / Мои круги».
4. Описание желаемой вещи, обязательные ограничения и необязательные предпочтения.
5. Объяснимое сопоставление предложений с пожеланиями.
6. Реальный поиск циклов длиной 2, 3 и 4 с разными владельцами.
7. Наглядную схему и текстовое описание передач для каждого участника.
8. Сохранённый круг, индивидуальные ответы, согласование всеми участниками.
9. Отказ, понятную причину распада и поиск другого варианта.
10. Сохранение данных, защиту от устаревших заявок и конфликтующих согласований.
11. Воспроизводимые демонстрационные данные, проверки и инструкции показа.

В первую версию не включай чат, оплату, доставку, оценки пользователей, социальную ленту, загрузку фото, геокодирование, внешние карты, сложную регистрацию, нейросетевые рекомендации и оптимизацию распределения всех вещей города. Контакты и точные домашние адреса для демонстрации не нужны.

Одна заявка соответствует одной отдаваемой вещи или неделимому комплекту. У пользователя может быть несколько заявок, но в одном круге он участвует только с одной из них. Прямой обмен — полноценный вариант длиной 2.

## 5. Сценарии и страницы

Сделай продуктовую главную страницу «Круг», а Data Studio перенеси на `/studio`. Обнови существующий браузерный тест студии под новый адрес. Администраторский инструмент не должен быть обязательным шагом для создания обычной заявки.

Достаточный набор страниц:

| Адрес | Назначение |
| --- | --- |
| `/` | Краткое объяснение сервиса, каталог, город, кнопка «Добавить заявку», вход в демо. |
| `/listings/new` | Форма «Что отдаю → Что хочу → Условия». |
| `/listings/[id]` | Подробности заявки и доступные владельцу действия. |
| `/listings/[id]/edit` | Та же форма в режиме редактирования. |
| `/matches?listingId=...` | Результаты поиска для моей заявки; варианты на 2, 3 и 4 участников. |
| `/circles/[id]` | Схема круга, мои передачи, причины совпадений, ответы и история состояния. |
| `/my` | Мои заявки и сохранённые круги с понятными статусами. |
| `/studio` | Существующий локальный редактор базы. |

Не заставляй пользователя заранее знать слово «граф» или устройство MongoDB. Для каждого состояния дай очевидный следующий шаг: добавить заявку, уточнить пожелания, посмотреть вариант, подтвердить, отказаться или искать снова.

Для пустого поиска покажи, какие условия использовались, и предложи пользователю самому изменить пожелания или ограничения. Сервис не должен тайно ослаблять обязательные условия.

## 6. Пользователь и серверная сессия

Для локального прототипа достаточно гостевого профиля: отображаемое имя, город Владивосток, удобная территория. Полноценное восстановление аккаунта не входит в MVP; обозначь это ограничение в документации.

Используй серверную сессию с непрозрачным случайным токеном в HttpOnly-cookie, `SameSite=Lax`, ограниченным сроком действия и `Secure` при HTTPS. Храни в MongoDB хеш токена и срок действия. TTL-индекс помогает удалять старые сессии, но сервер сам проверяет срок при каждом обращении.

Текущий пользователь определяется на сервере по сессии. `ownerId`, `userId` или участник, присланные в JSON/заголовке, не доказывают право действовать от этого лица. Чужую заявку нельзя изменить, а за другого участника нельзя подтвердить круг.

Демопереключатель доступен только при явно включённом `DEMO_MODE` в локальном режиме. Он выбирает только заранее созданные демопрофили и устанавливает их настоящие серверные сессии. В интерфейсе заметно обозначь «Демонстрация» и текущее имя. Переключение демоперсоны — не механизм входа в произвольный реальный аккаунт.

Сохрани локальное ограничение доступа приложения. Публичное размещение и полноценная аутентификация реальных пользователей — отдельный этап, который этот прототип не должен изображать завершённым.

## 7. Заявка и условия

Основные данные заявки:

- владелец, заголовок, текстовое описание отдаваемой вещи;
- категория и конкретный тип вещи из небольшого расширяемого справочника;
- состояние: новое / отличное / хорошее / с недостатками / требует ремонта;
- описание того, что хочется получить;
- допустимые типы/категории получаемой вещи, обязательные и исключённые признаки, необязательные предпочтения;
- территория нахождения вещи, допустимые территории общей встречи;
- при необходимости — доступные временные интервалы;
- максимальная длина круга: 2, 3 или 4;
- статус, версия содержимого, даты создания и изменения.

Форма должна оставаться короткой: текстовые описания — основные поля, редкие ограничения раскрываются дополнительно. Для известных слов предложи распознанные типы и теги, которые человек может проверить и исправить. При неопределённости предложи уточнение, а не молча назначай неправильную категорию.

Территории — редактируемый справочник удобных зон встречи Владивостока; назови их именно зонами, если используешь бытовые названия вроде «Центр», «Вторая Речка», «Чуркин», «Эгершельд», «остров Русский». Не выдавай такой список за официальное административное деление. Вариант «Весь город» означает отсутствие ограничения по зоне.

Для крупной вещи условие самовывоза должно влиять на допустимую общую зону встречи. Не вычисляй вымышленные километры и время в пути из названий территорий. Учитывай время в `Asia/Vladivostok`; API передаёт даты в ISO, а интерфейс однозначно показывает местное время.

Интервалы доступны как структурированное уточнение; свободный текст условий остаётся видимым участникам, но не выдаётся за автоматически проверенное ограничение.

## 8. Сопоставление текста и обязательных условий

Вынеси сопоставление в чистые функции, независимые от Express и MongoDB. Основной режим детерминированный и воспроизводимый.

Используй нормализацию русского текста: регистр, `ё/е`, пунктуацию, разумные стоп-слова и небольшой явный словарь форм/синонимов для демонстрационных типов. Например, «велосипед / велик», «монитор / дисплей»; не считай разные инструменты автоматически взаимозаменяемыми.

Структурированный тип вещи имеет преимущество перед случайным совпадением слова в описании. Общая категория «электроника» сама по себе не доказывает, что телевизор подходит человеку, который хочет монитор.

Сначала проверяй жёсткие условия: доступность, другой владелец, допустимый тип/категория, состояние, обязательные и исключённые признаки. Затем рассчитывай предпочтительность по совпадениям и явным мягким пожеланиям. Цена, если когда-нибудь появится, не должна сама решать за пользователя, какой обмен ему выгоден.

Отрицания нельзя терять при нормализации: «не нужен велосипед» не должно превращаться в положительное пожелание велосипеда. Поддержи ограниченный понятный разбор отрицаний или запроси явное уточнение исключений. Недостаток данных не равен доказанному соответствию.

Для каждого допустимого ребра возвращай причины и границы проверки: «тип: велосипед», «состояние подходит», «совпали признаки», «личные условия нужно уточнить». Внутренний score — инструмент сортировки, а не вероятность успешного обмена. Не показывай неподтверждённые «97% совместимости».

Сохрани возможность позже заменить нормализацию/оценку отдельным семантическим адаптером, но не добавляй сейчас обязательный внешний ИИ сервис и не поручай ему соблюдение жёстких ограничений или поиск циклов.

## 9. Граф и направление передачи

Вершина — конкретная активная заявка. Владелец — атрибут вершины.

Ребро `A → B` означает: **вещь из A подходит пожеланиям владельца B, и эта вещь передаётся от A к B**. Не используй одновременно противоположную трактовку «A хочет вещь B».

Для цикла `[v0, v1, ..., vk-1]`:

- каждый отдаёт собственную вещь следующему участнику;
- каждый получает вещь предыдущего;
- обязательно существует замыкающее ребро последнего к первому;
- длина только 2, 3 или 4;
- все заявки и все владельцы различны;
- круг содержит выбранную текущим пользователем заявку.

Проверочный пример:

```text
A: отдаёт монитор, хочет велосипед
B: отдаёт велосипед, хочет дрель
C: отдаёт дрель, хочет монитор

Передача вещей: A → C → B → A
A получает велосипед от B.
C получает монитор от A.
B получает дрель от C.
```

Порядок `A → B → C → A` для этих данных неверен. Проверь эту ориентацию в алгоритме, API, схеме и тестах.

Реализуй ограниченный DFS по спискам смежности с глубиной до 4. Не перебирай без необходимости все перестановки всех городских заявок и не строй отдельную графовую инфраструктуру.

Дедупликация учитывает циклический сдвиг: `[A,C,B]`, `[C,B,A]` и `[B,A,C]` — один круг. Обратный порядок не считается тем же ориентированным циклом, если не проверены его собственные рёбра. Сигнатура должна однозначно кодировать упорядоченные ID и версии, без неоднозначного склеивания строк.

## 10. Совместимость всего круга

Рёбер недостаточно. Перед выдачей результата проверь:

1. Длина не превышает ограничения ни одного участника.
2. Есть общая допустимая зона встречи всех участников с учётом самовывоза.
3. Если заданы временные ограничения, есть общее подходящее окно для всего круга, а не только попарные пересечения. Отсутствие ограничения означает гибкость, а не отсутствие доступности.
4. Все вещи по-прежнему доступны и не закреплены за другим согласованным кругом.
5. Нет повторного владельца под разными заявками.

Для прототипа считаем один круг одной координируемой встречей. Это осознанное упрощение; цепочки независимых доставок не входят в MVP.

Сортируй допустимые варианты воспроизводимо: сначала меньшая сложность координации, затем качество слабейшего совпадения, затем средняя оценка и стабильный ключ. Дай пользователю фильтр по 2/3/4 участникам, чтобы варианты длиной 4 не исчезали за большим числом пар.

Ограничь вход поиска, число результатов и объём обхода. Конкретные лимиты вынеси в конфигурацию. При достижении лимита явно верни `truncated` и объяснение; не выдавай неполный поиск за доказательство отсутствия кругов. На полном учебном наборе поиск должен быть исчерпывающим.

## 11. Доменные модели и MongoDB

Добавь отдельные типизированные модели и Zod-схемы. Предлагаемые коллекции:

| Коллекция | Содержимое |
| --- | --- |
| `krug_users` | Профиль, признак демо, идентификатор демонабора. |
| `krug_sessions` | Хеш токена, пользователь, срок действия. |
| `krug_listings` | Отдаваемая вещь, пожелания, ограничения, владелец, статус и версия. |
| `krug_circles` | Порядок заявок, версии и снимки условий, участники и ответы, общий статус, срок, даты. |
| `krug_events` | Небольшой журнал доменных событий для истории и измерений, без секретов. |

Названия можно уточнить при реализации, сохраняя отделение домена от студии. Для необходимых связей используй ObjectId в MongoDB, строки ID в API, явные сериализаторы и UTC-даты.

В круге удобно хранить до четырёх участников и их ответы вложенно. Сохраняй снимок показанных условий и версии исходных заявок: согласие относится к конкретному содержимому.

Индексы нужны по реальным запросам: активные заявки и категории/типы, владелец/дата, участники круга/статус, уникальная версионная сигнатура круга, срок сессии. Не пытайся сделать уникальность элементов массива между документами обычным уникальным индексом на весь массив без проверки семантики MongoDB.

Динамический редактор не должен произвольно менять `krug_*`, сессии или бизнес-статусы. Добавь серверную защиту зарезервированного пространства коллекций во всех универсальных маршрутах, включая чтение списка. Старые пользовательские коллекции сохрани. Демоданные домена создавай через специальный seed и доменные сервисы.

Сначала проверь коллизии имён с существующими данными. Не удаляй, не переименовывай и не перезаписывай неизвестные коллекции ради удобства новой схемы.

## 12. Состояния и согласование

Заявка: `active`, `reserved`, `archived`. Резервирование связано с конкретным кругом.

Круг: `proposed`, `agreed`, `declined`, `cancelled`, `expired`, `invalidated`. Ответ участника: `pending`, `accepted`, `declined`. Опиши допустимые переходы как часть домена и покрой их тестами.

Поиск возвращает кандидатов; просмотр результата ничего не резервирует. При выборе варианта сервер заново проверяет его и создаёт или возвращает существующий круг по версионной сигнатуре. Не создавай дубликаты при двойном клике.

Участник может подтвердить только свой интерес. Пока не согласились все, статус остаётся `proposed`. Для данного MVP «все согласились» означает готовность договариваться о передаче, а не доказательство фактической передачи вещей.

После последнего согласия сервер ещё раз проверяет заявки и в одной атомарной операции домена переводит круг в `agreed`, закрепляет все его вещи и делает недоступными конкурирующие варианты с этими вещами.

Отказ любого участника переводит круг в `declined`. Уже данные согласия не переносятся в новый круг. Отклонённая комбинация той же версии исключается из следующей выдачи; остальные варианты с этими людьми остаются возможны. Не архивируй заявку отказавшегося пользователя автоматически.

Изменение или архивирование исходной заявки делает предложения на старой версии недействительными. Изменять уже закреплённую вещь без предварительной отмены согласованного круга нельзя.

Участник может отменить согласованный круг; освобождение его вещей и изменение состояния должны быть согласованы. Используй ограниченный срок резервирования, например 24 часа, заданный в конфигурации. Истечение проверяется сервером и освобождает вещи. TTL-удаление документа не заменяет переход бизнес-состояния и журнал истории.

Повтор той же команды должен быть идемпотентным или давать предсказуемый конфликт. При конфликте показывай актуальное состояние и возможность нового поиска, а не ложное сообщение об успехе.

## 13. Атомарность — учти текущий standalone

Сейчас `mongod` запускается как standalone. Не добавляй `withTransaction`, оставив прежний запуск: [многодокументные транзакции в таком режиме не работают](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/).

Для локального MVP подготовь replica set из одного узла:

- настрой `mongod` с именем replica set и loopback-привязкой;
- добавь идемпотентную инициализацию и ожидание PRIMARY;
- обнови URI и `.env.example` согласованно;
- проверь запуск с существующим каталогом данных и сохранность студии;
- корректно останови старый процесс перед переключением режима, не удаляя файлы базы;
- опиши переход и возможность резервной копии в README.

Это средство локальных транзакций, не решение высокой доступности для продакшена. Используй существующий драйвер MongoDB и его штатные сессии; новый ORM не нужен.

Изменения ответа, последнего согласия, резервирования нескольких вещей, отмены и инвалидирования выполняй с корректными транзакциями и проверкой ожидаемых версий/статусов. Не ограничивайся предварительным чтением «ещё свободно», после которого несколько запросов могут одновременно записать успех.

Не запускай параллельные операции через `Promise.all` внутри одной транзакционной сессии. Обработай повторяемые конфликты, idempotency и итоговые 409. Два конкурирующих согласования одной вещи не могут оба закончиться `agreed`, в том числе при двух одновременных последних ответах.

Если найдёшь действительно более простой дизайн с той же проверенной атомарностью на standalone, сначала зафиксируй его инварианты и докажи их интеграционными тестами, включая гонки и перезапуск. Набор независимых `updateOne` и блокировка только в памяти такими доказательствами не являются.

## 14. Архитектура и контракты

Расширяй существующий сервер. Раздели чистую предметную логику, работу с MongoDB и HTTP-контроллеры. Ориентир:

```text
shared/krug/                 # DTO, схемы запросов и общие типы
server/domain/krug/          # сопоставление, граф, ограничения, состояния
server/repositories/krug/    # типизированная работа с MongoDB
server/services/krug/        # согласование, поиск, сессии, транзакции
server/routes/krug/          # HTTP и преобразование ошибок
server/scripts/             # инициализация, seed и безопасный сброс демо
src/components/krug/        # продуктовые формы, карточки и схема круга
src/lib/krug-api.ts          # типизированный клиент
src/app/...                 # маршруты продукта и /studio
tests/                      # алгоритм, интеграция, браузерные сценарии
```

Не создавай слои ради слоёв: небольшие модули можно объединить, если сохранены границы и тестируемость. Сохрани текущие серверный `tsconfig`, общий пул подключения и обработку ошибок.

Для нового домена выдели `/api/krug/*`, для демосессий — отдельный явно ограниченный маршрут. Добавь нужный rewrite, не сломав `/api/db/*`. Согласуй cookies и заголовки при проксировании.

Учти особенность текущего `server/app.ts`: проверка `X-DB-Client` сейчас глобальная и перехватывает все изменяющие запросы. Раздели общую защиту локального доступа и специфичные middleware студии и продукта; новый API не должен случайно получать 403 или использовать служебный заголовок вместо пользовательской сессии.

Минимальные действия API:

| Действие | Требования |
| --- | --- |
| Сессия: текущая / гостевая / выход | Токен на сервере, cookie, срок действия. |
| Справочники | Категории, типы, состояния, зоны встречи. |
| Список и детали заявок | Пагинация, фильтры, безопасное представление пользователя. |
| Создать / изменить / архивировать заявку | Владелец из сессии, версия, повторная валидация, инвалидирование старых кругов. |
| Поиск по моей заявке | 2–4 участника, объяснения, ограничения, длительность и признак неполноты поиска. |
| Создать / получить / перечислить мои круги | Сервер пересчитывает валидность перед сохранением. Детали ответов доступны участникам. |
| Ответить на круг | Только текущий участник, идемпотентность и атомарность последнего согласия. |
| Отменить круг | Участник, журнал, освобождение закреплённых вещей. |
| Демосмена пользователя | Только локальный деморежим и только профили демонабора. |

Зафиксируй точные URL и DTO до параллельной работы фронтенд- и бэкенд-разработчиков. Возвращай понятные коды: 400 — данные, 401 — нет сессии, 403 — нет прав, 404 — объект недоступен, 409 — конфликт, 429 — лимит, 503 — зависимость недоступна. Не выдавай любой программный дефект за ошибку подключения MongoDB; внутренние ошибки диагностируются отдельно.

## 15. Базовая безопасность и ошибки

Серверная Zod-валидация — обязательная. Ограничь длины текстов, количество признаков/интервалов, страницы и результаты поиска. Данные клиента не должны становиться произвольным MongoDB-фильтром или update-оператором.

Проверяй авторизацию объекта на каждом изменении и чтении приватного круга. Сохрани защиту Origin/Host и от межсайтовых изменяющих запросов. Служебный заголовок сам по себе не аутентификация. Не добавляй `Access-Control-Allow-Origin: *` для обхода проблем cookies.

Тексты заявок выводи как текст, без `dangerouslySetInnerHTML`. Не логируй cookie, токены, строки подключения с паролем и личные условия целиком. `.env` и файлы базы остаются вне Git; `.env.example` содержит только безопасные примеры.

Для создания сессий и затратного поиска добавь соразмерное локальному MVP ограничение частоты. Не подключай Redis только ради rate limit: один процесс API достаточен для прототипа, а ограничения такого решения укажи в документации.

Реализуй состояния загрузки, пустоты, ошибок формы, недоступности API/базы, конфликта изменённой заявки и повторного запроса. Успешный интерфейсный статус появляется после ответа сервера.

## 16. Интерфейс и визуализация

Язык — русский, название — «Круг», город — Владивосток. Человек должен быстро понять: что у него есть, что он получит и что требуется сделать дальше.

Визуальное направление: спокойный светлый интерфейс, тёплый нейтральный фон, читаемая типографика, зелёный основной акцент, умеренные дополнительные цвета для участников. Можно переиспользовать действующие CSS-переменные и доступные диалоги. Изолируй стили Data Studio, чтобы его общие селекторы не ломали продукт.

Примени Material Design 3 из проектного навыка: семантические цветовые роли, тональные поверхности, согласованную шкалу типографики и форм, выразительные приоритетные действия и доступные состояния. Мобильную оболочку реализуй на Framework7 React с `theme: 'md'`; десктопную — на тематизированных Material UI компонентах. Прочитай справочник навыка `references/framework7-mobile.md`, проверь совместимость стабильных зависимостей с текущим React и Next.js. Стартовые токены перенеси в общий исходный модуль приложения, затем отобрази в тему MUI и CSS-переменные Framework7; проверь контраст.

Раздели представления с общими hooks/сервисами и состоянием форм. Начальный порог оболочек — 840 px, вынесенный в конфигурацию. Выбери одного владельца URL/history и проверь deep links, Back и reload. При необходимости браузерной загрузки Framework7 отключай SSR только его клиентской оболочке со стабильным fallback. Не монтируй одновременно два полноценных интерфейса с независимыми обработчиками. Изолируй CSS и root-эффекты Framework7 от MUI и `/studio`, сохраняй черновик и сессию при смене ширины.

На главной достаточно компактного объяснения из трёх шагов и реальных заявок. Не подменяй работающий продукт большим рекламным экраном. Для MVP нужны текстовые карточки и иконки категорий; фото и внешние изображения не обязательны.

Карточка заявки показывает «Отдаёт», «Хочет», зону и существенные условия. Карточка результата — количество участников, что получит текущий пользователь, причины совместимости и кнопку просмотра.

Для 2–4 участников сделай собственную компактную SVG-схему или простую вёрстку с направленными стрелками. Тяжёлый графовый редактор здесь не нужен. У каждого узла: имя, отдаваемая вещь и статус ответа. На ребре понятно, какая вещь кому передаётся.

Выдели текущего пользователя и отдельно напиши: «Вы отдаёте … участнику …» и «Вы получаете … от участника …». Порядок в списке, подписи стрелок и серверные DTO должны совпадать.

На мобильном экране дай последовательный текстовый список передач и компактную схему, не требующую горизонтальной прокрутки всей страницы. Диаграмма не должна быть единственным способом понять круг. Обеспечь клавиатуру, подписи элементов, контраст и учёт `prefers-reduced-motion`.

После каждого ответа обновляй статусы у остальных открытых участников: для MVP достаточно ограниченного polling с остановкой в фоне и при размонтировании. WebSocket-инфраструктура не обязательна.

## 17. Воспроизводимые демоданные

Подготовь явно вымышленных участников A–L и согласованные типы вещей. Все базовые условия совместимы, время встречи — будущее относительно запуска и корректно показано по Владивостоку.

| ID | Отдаёт | Хочет |
| --- | --- | --- |
| A | монитор | велосипед |
| B | велосипед | дрель |
| C | дрель | монитор |
| D | велосипед | рюкзак |
| E | рюкзак | монитор |
| F | гитара | книги |
| G | книги | фотоаппарат |
| H | фотоаппарат | лампа |
| I | лампа | гитара |
| J | чайник | тостер |
| K | тостер | чайник |
| L | шлем | швейная машинка |

После добавления заявки A полный учебный граф должен дать ровно четыре цикла с точностью до циклического сдвига:

```text
A → C → B → A
A → E → D → A
F → I → H → G → F
J → K → J
```

У A прямой пары нет. После отказа B от первого круга остаётся вариант `A → E → D → A`. У L нет круга. Эти ожидания вытекают из данных, а не подставляются в обработчик поиска по ID.

Для основной демонстрации seed создаёт пользователей A–L и 11 заявок B–L. Заявку A ведущий создаёт через обычную форму. Для алгоритмических тестов используй полный набор из 12 заявок.

Имена, зоны и описания придумай правдоподобные, без реальных контактов. Обозначь демонабор. Идентификаторы фикстур должны быть стабильными для идемпотентного заполнения, но алгоритм не должен знать их бизнес-значение.

Добавь `demo:seed` и `demo:reset`. Повторный seed не создаёт дубликаты и не откатывает пользовательские изменения. Reset затрагивает только явно помеченный демонабор и его связанные записи, не вызывает `dropDatabase` рабочей базы и не удаляет произвольные коллекции. Для времени не используй фиксированную дату, которая скоро окажется в прошлом.

## 18. Метрики и проверка гипотезы

Добавь компактный результат сравнения на одном и том же наборе заявок и при одинаковых условиях:

- сколько уникальных владельцев/заявок имеют хотя бы один допустимый прямой обмен;
- сколько имеют хотя бы один допустимый круг длиной 2–4;
- сколько дополнительно получили потенциальный вариант благодаря длине 3 или 4;
- длительность поиска и полнота обхода;
- для пилота — поиски, просмотры вариантов, ответы, отказы и согласованные круги.

Покрытие считай по уникальным ID, не суммированием длин пересекающихся кругов. Возможность участия хотя бы в одном варианте не означает, что все найденные круги могут быть выполнены одновременно. Глобальную оптимальную упаковку непересекающихся кругов в MVP не обещай.

При поиске только по одной заявке показывай её результат. Общие показатели демонабора рассчитывай отдельно и обозначай область сравнения. Неполный обход нельзя использовать как точную общегородскую статистику.

Согласованный круг — не состоявшийся обмен. Не показывай выдуманную экономию денег, тонны спасённых вещей, CO₂, статистику Владивостока или отзывы. Демопоказатели явно помечай, реальные выводы оставь будущему пилоту.

## 19. Тесты, которые доказывают работу

Сохрани существующие проверки студии. Новые тесты должны проверять бизнес-инварианты и реальные интеграции.

### Чистая логика

- Прямой обмен и циклы на 3 и 4 участников; отсутствие циклов.
- Исходный пример с правильным направлением передачи.
- Повторные вершины и два объявления одного владельца не образуют допустимый круг.
- Открытая цепь, петля на себя и длина 5 не выдаются.
- Циклические повороты дедуплицируются; направление не теряется.
- Нормализация русского текста и поддержанные синонимы работают; отрицания и исключения не превращаются в положительный матч.
- Неверный тип или состояние отсекаются до ранжирования.
- Попарно совместимые условия без общей зоны/времени всего круга не проходят.
- Ограничение любого участника длиной 2 или 3 соблюдается.
- Неактивные, архивированные и закреплённые вещи исключаются.
- Синтетический набор A–L даёт ровно ожидаемые циклы и альтернативу после отказа.

### Интеграция с настоящей MongoDB

- Сессия, истечение, отсутствие прав, чужое изменение и чужой ответ.
- Создание заявки и чтение после нового подключения.
- Повторное создание одного круга не создаёт дубликат.
- Частичные согласия не дают `agreed`; последнее согласие согласует весь круг.
- Отказ и новый поиск не возвращают ту же отклонённую версию круга.
- Изменение/архивирование заявки инвалидирует старое предложение.
- Два конкурентных круга с одной вещью не согласуются одновременно.
- Одновременные последние ответы не теряются и не резервируют вещи дважды.
- Отмена, истечение и повтор запросов сохраняют согласованное состояние.
- Универсальное API Data Studio не обходит доменные ограничения `krug_*`.
- Некорректный JSON, ID, оператороподобный ввод и превышенные лимиты дают ожидаемую ошибку.

Тесты работают в изолированной временной базе и удаляют только её. Для транзакционных тестов нужна фактически работающая конфигурация replica set, а не мок, который всегда возвращает успех.

### Браузер

1. Войти в демо как A, добавить монитор с пожеланием велосипеда.
2. Найти трёхсторонний круг и убедиться, что A получает именно велосипед.
3. Открыть сохранённый круг, подтвердить от A.
4. В отдельной сессии/контексте подтвердить от C, затем от B; увидеть `agreed` у всех.
5. Проверить отдельно сценарий отказа B и новый вариант через E и D.
6. Показать круг на 4, прямую пару и отсутствие варианта у L.
7. Проверить мобильную оболочку Framework7: tabbar, sheet/popup, клавиатуру, ошибки формы, Back, прямую ссылку, обновление страницы и отсутствие ошибок JavaScript. Повторить основной сценарий на десктопной MUI-оболочке и проверить сохранность состояния при смене ширины.

Не проверяй всех пользователей одним подделанным `userId`. В браузерном тесте нужны отдельные контексты с настоящими сессиями. Демопереключатель используется только в соответствующем режиме.

Измерь время поиска на воспроизводимом синтетическом наборе. Укажи размер графа, параметры, среду и фактическое время; не записывай обещание масштабирования вместо измерения. Жёсткий короткий таймер в unit-тесте не должен делать корректные тесты случайно падающими на медленном компьютере.

## 21. Этапы выполнения

Веди короткий `docs/implementation-plan.md` со статусами, критериями готовности и обнаруженными ограничениями. Не превращай его в пересказ каждого действия.

1. **Проверка основы.** Прочитать актуальный репозиторий, проверить запуск и текущие данные. Перенести Data Studio на `/studio`, сохранить его сценарий и ограничения доступа. Готово: студия открывается и её тест проходит.
2. **Домен и алгоритм.** Зафиксировать DTO, модели, ориентацию графа, состояния и фикстуры. Реализовать чистые функции сопоставления, общих условий, DFS и дедупликации. Готово: ожидаемые 2/3/4 циклы и отрицательные случаи проходят тесты.
3. **База, сессии и API.** Подготовить replica set, индексы, идемпотентный seed, авторизацию владельца, сохранение заявок и кругов, транзакционное согласование. Готово: реальный сценарий проходит интеграционные тесты, включая гонку.
4. **Интерфейс.** Реализовать каталог, формы, поиск, схему, мои круги и ответы. Готово: браузер создаёт заявку и согласует круг реальными сессиями.
5. **Отказ и устойчивость.** Завершить альтернативный поиск, инвалидирование, отмену, истечение, ошибки и мобильную версию. Готово: отказ B приводит к другому рабочему кругу, состояние переживает обновление и перезапуск.
6. **Показ и качество.** Проверить чистый запуск, измерения, основной сценарий и документацию. Исправить выявленные дефекты. Готово: команда может повторить показ по README без ручной правки базы.

После этапа выполняй подходящие проверки и исправляй выявленные дефекты. Мелкие неоднозначности решай самостоятельно и записывай допущения. Отдельного ответа пользователя требуют только действительно отсутствующие внешние доступы или решение, без которого нельзя безопасно продолжить.

Также запусти добавленные тесты домена, конкурентных действий и демонстрационных данных. Проверь запуск после остановки и сохранность обычных записей. Если браузер или другая зависимость недоступны, точно укажи непроведённую проверку и причину.

### Обязательные критерии готовности

- Заявка создаётся через обычную форму и сохраняется в MongoDB.
- Поиск работает на текущих данных и находит циклы 2, 3 и 4, а не заготовленные ID.
- Для A после добавления монитора нет прямого обмена, но есть `A → C → B → A` и `A → E → D → A`.
- Каждый видит правильную отдаваемую и получаемую вещь.
- Только соответствующий пользователь может ответить за себя.
- Все согласия приводят к единому согласованному состоянию; вещь не закрепляется одновременно за двумя кругами.
- Отказ B не возвращает тот же круг в той же версии и позволяет найти альтернативу через E и D.
- Архивирование, изменение и резервирование не оставляют ложных доступных результатов.
- Жёсткие ограничения не нарушаются ради красивой выдачи.
- Обновление и перезапуск не стирают заявки и ответы.
- Существующий Data Studio доступен на `/studio` и не обходит защиту доменных коллекций.
- Демо воспроизводится без внешней LLM, реальных телефонов и ручной правки документов.
- Статистика честно отделяет потенциал, согласие и фактический обмен.
- Тесты, инструкции показа и фактические ограничения записаны в документации.

Не заявляй готовность, если главный сценарий работает только на моках, только до перезагрузки, без проверки владельца или без корректного последнего подтверждения.
